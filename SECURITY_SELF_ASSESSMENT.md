## Overview

k8sgpt scans Kubernetes clusters with analyzers that codify SRE knowledge, and can optionally send
the findings to a user-chosen AI backend to explain them in plain language.

### Background

Diagnosing Kubernetes failures (crash-looping Pods, failed rollouts, misconfigured Services and
Ingresses, and so on) needs both cluster access and operational experience. k8sgpt reads cluster state
through the Kubernetes API, runs built-in and optional custom analyzers over it, and produces findings.
With `--explain`, findings are sent to an LLM provider (hosted, such as OpenAI, Azure OpenAI, Amazon
Bedrock, Google Gemini or Cohere, or self-hosted, such as Ollama or LocalAI) for an explanation.
k8sgpt runs as a CLI, as a long-running server (`k8sgpt serve`, gRPC/HTTP API and an optional MCP server),
and inside clusters through the k8sgpt-operator.

### Actors

1. **k8sgpt CLI.** Runs on a user workstation or CI runner with the user's kubeconfig. Isolation: it has
   exactly the Kubernetes permissions of that kubeconfig.
2. **k8sgpt server (`k8sgpt serve`).** Exposes the analysis API over gRPC with an HTTP gateway, plus an
   optional MCP server (default port 8089). Isolation: separate process/Pod; it uses its own ServiceAccount
   or kubeconfig. See the TODO under [Security functions and features](#security-functions-and-features)
   about authentication on these ports.
3. **k8sgpt-operator.** A Kubernetes controller that deploys the k8sgpt server in-cluster, schedules
   analyses from `K8sGPT` custom resources, and writes `Result` resources. Optionally (alpha, off by default)
   it creates `Mutation` proposals and applies narrowly allow-listed changes (auto-remediation).
   Isolation: its own ServiceAccount and RBAC from the Helm chart / manifests.
4. **AI backend.** An external or self-hosted LLM endpoint. It receives finding text when explanation is
   enabled. Isolation: network boundary; authenticated with the user's API key.
5. **Kubernetes API server.** Source of cluster state; authorizes every k8sgpt request with RBAC.
6. **Custom analyzers.** Optional user-operated gRPC services that k8sgpt calls for extra analysis.
7. **Remote cache.** Optional S3, Azure Blob, GCS or Interplex store for analysis results.
8. **Integrations.** Optional integrations built into the CLI (`pkg/integration`: Prometheus, Keda, Kyverno, AWS) and those listed in
   [INTEGRATIONS.md](https://github.com/k8sgpt-ai/k8sgpt/blob/main/INTEGRATIONS.md)).

### Actions

1. **Connect:** the CLI or server builds a Kubernetes client from kubeconfig or in-cluster config; the API
   server authenticates and authorizes every call.
2. **Analyze:** analyzers list and read resources and events for the selected filters and namespaces, and
   produce findings. Analysis itself does not write to the cluster.
3. **Anonymize (optional):** with `--anonymize`, object names and labels in findings are replaced with
   keys before being sent to the AI backend, and restored in the output. This is **off by default** and,
   per the flag help text, does not currently apply to Kubernetes events.
4. **Explain (optional):** with `--explain`, findings (anonymized or not) are sent to the configured AI
   backend over HTTPS using the configured credentials; responses can be cached locally or remotely.
5. **Serve:** `k8sgpt serve` accepts analysis and configuration requests over gRPC/HTTP and MCP.
6. **Operator reconcile:** the operator reads `K8sGPT` resources and the referenced backend Secret, calls
   the in-cluster k8sgpt server, and stores `Result` resources.
7. **Auto-remediation (operator, alpha, off by default):** for allow-listed resource types, the operator
   creates a `Mutation` proposal. Before executing, it re-fetches the target and only applies a single-path
   container image change that passes the policy gate (same GVK/name/namespace/UID/resourceVersion), after a
   server-side dry run; everything else is aborted and left as a proposal
   ([AUTO_REMEDIATION.md](https://github.com/k8sgpt-ai/k8sgpt-operator/blob/main/AUTO_REMEDIATION.md)).

### Goals

- Help users of any experience level understand Kubernetes failures quickly.
- Read-only analysis: the CLI and server analyzers do not modify cluster state.
- Let users choose their AI backend, including self-hosted models so that data does not leave their network.
- Offer anonymization so that object names and labels need not be shared with an AI backend.
- Respect Kubernetes RBAC: k8sgpt only sees what its credentials allow.
- For the operator's optional auto-remediation, apply only changes that pass a deterministic,
  deny-by-default policy gate.

### Non-goals

- k8sgpt is not a security or compliance scanner; it does not try to find vulnerabilities in workloads.
- k8sgpt does not guarantee the accuracy of AI-generated explanations; they are advisory.
- k8sgpt does not provide or host an AI model; data sent to a hosted backend is governed by that provider.
- The CLI and server do not remediate. Remediation exists only in the operator, is alpha, off by default,
  and is not intended for production changes without independent review.
- k8sgpt does not manage or rotate AI backend credentials.

## Self-assessment use

This self-assessment is created by the k8sgpt team to perform an internal analysis of the project's
security. It is not intended to provide a security audit of k8sgpt, or function as an independent
assessment or attestation of k8sgpt's security health.

This document serves to provide k8sgpt users with an initial understanding of k8sgpt's security, where to
find existing security documentation, k8sgpt plans for security, and general overview of k8sgpt security
practices, both for development of k8sgpt as well as security of k8sgpt.

This document provides the CNCF TAG Security and Compliance with an initial understanding of k8sgpt to
assist in a joint-assessment, necessary for projects under incubation. Taken together, this document and
the joint-assessment serve as a cornerstone for if and when k8sgpt seeks graduation and is preparing for a
security audit.

## Security functions and features

### Critical

| Component | Description |
| -- | -- |
| Kubernetes RBAC boundary | All cluster access goes through the Kubernetes API with the caller's credentials; k8sgpt cannot see more than its kubeconfig or ServiceAccount allows. |
| Read-only analysis | Analyzers only read resources and events; no analyzer writes to the cluster. |
| Auto-remediation policy gate (operator) | Deny-by-default; executes only a single allow-listed image-field change after re-fetch, UID/resourceVersion checks and a server-side dry run. |
| Transport to AI backends | Hosted backends are called over HTTPS using their Go SDKs/HTTP clients. **TODO (maintainers):** confirm no backend allows plaintext HTTP except explicitly configured local endpoints (e.g. LocalAI/Ollama base URLs). |

### Security relevant

| Component | Description |
| -- | -- |
| `--anonymize` | Masks object names and labels before sending to the AI backend. Off by default; does not cover events. |
| AI backend choice | Self-hosted backends (Ollama, LocalAI, custom REST) keep data inside the user's network. |
| Credential storage | AI API keys are stored in plaintext in `$XDG_CONFIG_HOME/k8sgpt/k8sgpt.yaml` (CLI) or a Kubernetes Secret referenced by the `K8sGPT` resource (operator). Users must restrict access to both. |
| `k8sgpt serve` network exposure | The gRPC API binds to `:<port>` on all interfaces and the in-process HTTP gateway dials it with insecure (plaintext) gRPC credentials ([pkg/server/server.go](https://github.com/k8sgpt-ai/k8sgpt/blob/main/pkg/server/server.go)). **TODO (maintainers):** document whether the server or MCP endpoint offers any authentication/TLS, and recommend NetworkPolicy or localhost binding. |
| Filters and namespaces | Users choose which analyzers run and which namespaces are read, limiting what data is processed. |
| Remote cache | Optional S3/Azure/GCS/Interplex; users supply and must protect the storage credentials. |
| Custom headers | Extra headers (e.g. for gateway authentication) can be added to AI requests. |

  [.github/settings.yml](https://github.com/k8sgpt-ai/k8sgpt/blob/main/.github/settings.yml)). Commits are not required to be cryptographically signed.
- **Review:** branch protection in `.github/settings.yml` requires 1 approving review, code owner review
  ([CODEOWNERS](https://github.com/k8sgpt-ai/k8sgpt/blob/main/.github/CODEOWNERS)), resolved conversations,
  linear history, and applies to admins. **TODO (maintainers):** confirm these settings are applied on GitHub.
- **Automated checks on PRs:** `go test ./...` with coverage (Codecov), golangci-lint, semantic PR title
  validation, container image build.
- **Dependencies:** Renovate opens dependency PRs (Go modules, GitHub Actions, Dockerfiles), with GitHub
  Actions pinned to commit digests (`helpers:pinGitHubActionDigests`).

  container image. The GoReleaser checksum file is signed with cosign keyless signing (Sigstore, GitHub OIDC),
  and the `.sigstore.json` bundle is published on the GitHub release. That signing step is added in the release
  workflow; releases published before it is on `main` are not signed. The container image is built in a separate
  job and is not signed by this step.

## Security issue resolution

### Responsible disclosure process

Described in [SECURITY.md](https://github.com/k8sgpt-ai/k8sgpt/blob/main/SECURITY.md): reports go through
GitHub private vulnerability reporting (enabled on k8sgpt-ai/k8sgpt) or contact@k8sgpt.ai; public issues and
Slack must not be used for vulnerabilities.

### Vulnerability response process

The Security Response Team defined in SECURITY.md and GOVERNANCE.md triages reports, assigns severity,
develops the fix in a private advisory fork, releases a patch, and publishes a GitHub Security Advisory.
Target timelines are in SECURITY.md. The Security Response Team is Alex Jones (@AlexsJones) and Anais Urlichs (@AnaisUrlichs).

### Incident response

1. **Triage:** the triage lead confirms the report and assigns severity.
2. **Confirmation:** the issue is reproduced and affected versions identified.
3. **Notification:** affected users are told through the published advisory, release notes and `#k8sgpt`
   on CNCF Slack.
4. **Patching:** a patch release on the latest release line is published (no backports; see SECURITY.md).

### Case studies

1. **Interactive troubleshooting:** an engineer runs `k8sgpt analyze --explain` against a cluster to find
   and explain failing workloads.
2. **Continuous in-cluster analysis:** a platform team deploys the operator so analyses run on a schedule and
   results are stored as `Result` resources and exposed to Prometheus.
3. **AI assistant integration:** a user connects an MCP client to `k8sgpt serve --mcp` so an assistant can
   run analyses on request.

- **HolmesGPT (CNCF Sandbox):** AI-assisted investigation across observability data; k8sgpt focuses on
  Kubernetes-native analyzers with optional AI explanation.
- **kube-linter, Polaris:** static checks of manifests; k8sgpt analyzes live cluster state.
- **Kubescape, Trivy:** security posture and vulnerability scanning; k8sgpt is an operational diagnostics tool.
